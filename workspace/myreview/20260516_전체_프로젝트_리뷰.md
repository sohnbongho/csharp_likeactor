# 코드 리뷰: csharp_likeactor 전체 프로젝트

날짜: 2026-05-16

## 총평

액터 모델 기반의 MMO 서버 골격으로, 동시성 설계(SessionId 기반 샤딩, Channel 기반 메시지 큐, 풀 재사용)는 체계적으로 잘 짜여 있다. 다만 게임 로직 영역에서 서버 권위 검증이 전혀 없어 클라이언트 치트에 취약하고, 인증 흐름의 race condition이 보안 결함으로 이어질 수 있으므로 실 서비스 전에 반드시 보완이 필요하다.

## 심각도별 지적 사항

### 🔴 심각 (버그·보안·데이터 손실 위험)

#### 1. RegisterAuthenticatedSession — 동시 로그인 Race Condition
**파일**: `Server/Actors/UserObjectPoolManager.cs:76-82`

```csharp
_authenticatedSessions.TryGetValue(userId, out var old);  // Step 1
_authenticatedSessions[userId] = newSession;              // Step 2
if (old != null && !ReferenceEquals(old, newSession))
    old.Disconnect();
```

두 TCP 연결이 동일한 userId로 동시에 로그인 성공하면:
- Thread A: Step1 → `old=null`
- Thread B: Step1 → `old=null`  
- Thread A: Step2 → `[userId] = SessionA`
- Thread B: Step2 → `[userId] = SessionB` (SessionA 덮어씀)
- 두 스레드 모두 `old == null`이므로 Disconnect 없음

**결과**: 같은 계정의 두 세션이 동시에 authenticated 상태가 되어 중복 로그인 허용.

**수정 방향**: `ConcurrentDictionary.AddOrUpdate`나 별도의 lock으로 TryGetValue+set을 원자적으로 처리.

#### 2. MoveRequestHandler — 서버 권위 좌표 검증 없음
**파일**: `Server/Actors/User/Handler/Remote/MoveRequestHandler.cs:14-23`

```csharp
var req = message.MoveRequest;
session.UpdatePosition(req.X, req.Y);  // 클라이언트 값 그대로 저장
receiver.Send(new MessageWrapper { MoveResponse = new MoveResponse { Success = true, X = req.X, Y = req.Y } });
```

- 클라이언트가 보내는 X, Y 좌표에 아무런 서버 검증(이동 속도, 맵 경계, 충돌)이 없음
- 순간이동, 벽 통과, 속도 핵 등 위치 조작에 무방비 상태
- `Success = true`를 무조건 반환하므로 클라이언트 측 검증도 우회 가능

**수정 방향**: 이전 위치와 경과 시간 기반으로 최대 이동 거리 검증 후 수용 여부 결정.

#### 3. GameOverReportHandler — 클라이언트 보고 스코어 무검증 저장
**파일**: `Server/Actors/User/Handler/Remote/GameOverReportHandler.cs:16-23`

```csharp
var report = message.GameOverReport;
session.EnqueueSqlRequest(new SaveScoreSqlRequest(
    session, session.AccountData.AccountId,
    report.Score, report.KillCount, report.SurviveSeconds));
```

- 클라이언트가 보고하는 점수/킬/생존시간을 서버에서 전혀 추적하지 않아 임의 값으로 1위 등재 가능
- 서버에서 게임 세션 상태를 전혀 관리하지 않으면 최소한 상한 값 검증이라도 필요

**수정 방향**: 서버에서 게임 시작~종료 사이 경과 시간, 인정 가능한 점수 범위를 추적해 비교 검증.

### 🟡 경고 (잠재적 문제·성능·동시성 위험)

#### 4. PasswordHashHelper — SHA-256 클라이언트 해시 전송 방식
**파일**: `Library/Security/PasswordHashHelper.cs:11-12`

```csharp
public static byte[] ComputeClientHash(string plainPassword)
    => SHA256.HashData(Encoding.UTF8.GetBytes(plainPassword));
```

- 클라이언트에서 `SHA256(password)`를 서버로 전송함
- TLS 없는 환경에서 네트워크 캡처로 해시를 얻으면 **재전송(replay) 공격** 가능
- SHA-256은 빠른 해시 함수라, 캡처한 해시로 PBKDF2 서버 검증을 직접 노리는 오프라인 brute force 가능
- 서버 PBKDF2(salt, 100,000회)가 저장 해시를 보호하더라도, 네트워크상 해시 = 실질적인 비밀번호

**수정 방향**: TLS(HTTPS/TLS TCP) 적용 후 평문 비밀번호를 서버에서 PBKDF2 처리. 또는 nonce 기반 challenge-response 방식 도입.

#### 5. AdminApiHost — Swagger UI 환경 구분 없이 항상 활성화
**파일**: `Server/AdminApi/AdminApiHost.cs:89-90`

```csharp

_app.UseSwaggerUI();
```

`SessionKeyMiddleware`가 `/swagger` 경로를 인증 면제로 처리하므로, 인증 없이도 API 명세 전체가 외부에 노출된다. 프로덕션 환경에서 어드민 API 구조가 공개되면 공격 벡터가 됨.

**수정 방향**: `app.Environment.IsDevelopment()` 조건으로 Swagger를 개발 환경에서만 활성화.

#### 7. EnterWorldRequestHandler — IsAuthenticated 직접 검증 부재
**파일**: `Server/Actors/User/Handler/Remote/EnterWorldRequestHandler.cs:13-27`

핸들러 내에서 `session.IsAuthenticated` 확인이 없어, 미인증 세션의 차단을 전적으로 `UserSession.IsBlockedBeforeAuth()`에 의존한다. 이 의존성은 코드상에서 드러나지 않아 유지보수 중 실수가 생기기 쉽다.

**수정 방향**: 핸들러 내 상단에 `if (!session.IsAuthenticated) return Task.FromResult(true);` 추가.

#### 8. LobbyThreadManager / WorldThreadManager — 순차 StopAsync
**파일**: `Library/World/LobbyThreadManager.cs:27-29`, `WorldThreadManager.cs:27-29`

```csharp
foreach (var w in _workers) await w.StopAsync(); // 순차 종료
```

워커 수만큼 직렬로 대기하므로 종료 시간이 워커 수에 비례해 늘어남.

**수정 방향**: `await Task.WhenAll(_workers.Select(w => w.StopAsync()))` 로 병렬 종료.

#### 9. ReceiveParser — 파싱 루프 상한 10,000 과다
**파일**: `Library/Network/ReceiveParser.cs:42`

```csharp
const int _maxParsingCount = 10000;
```

버퍼 크기(8192바이트)와 최소 메시지 크기(~3바이트)를 감안하면 실제 최대 파싱 수는 ~2700개이므로 10,000 상한은 의미가 없다. 더 심각한 것은 이 루프가 IO 쓰레드 풀에서 실행되는 `async void OnReceiveCompleted` 안에서 실행된다는 점이다. 파싱 수를 실용적인 값(예: 100)으로 낮추면 의도를 명확히 표현할 수 있다.

### 🔵 제안 (가독성·유지보수성·관례 개선)

#### 10. SaveScoreSqlRequest — null 강제 참조 연산자
**파일**: `Server/Actors/User/DbRequest/Sql/SaveScoreSqlRequest.cs:41`

```csharp
await Session!.EnqueueMessageAsync(...);
```

생성자에서 `null`을 받지 않지만, `ISqlRequest.Session`이 `nullable`로 선언되어 `!`를 써야 하는 구조. `Session`을 `IMessageQueueReceiver`(non-nullable)로 바꾸거나, 생성자 단계에서 null 체크를 추가하면 더 명시적.

#### 11. ObjectPool — Return() 시 크기 한도 없음
**파일**: `Library/ObjectPool/ObjectPool.cs:39-42`

```csharp
public void Return(T obj)
{
    _pool.Enqueue(obj); // 크기 확인 없이 enqueue

```

현 설계에서는 Rent한 만큼만 Return되므로 실제로 초과하지 않지만, 방어 코드가 없어 오용 시 메모리 누수 가능.

#### 12. SenderHandler — 단일 메시지씩 SendAsync
**파일**: `Library/Network/SenderHandler.cs:96-108`

큐에 여러 메시지가 있어도 1개씩 serialize → SendAsync 호출. 여러 메시지를 하나의 버퍼에 직렬화 후 단일 SendAsync를 사용하면 시스템 콜 수를 줄일 수 있다. (단, 코드 복잡도 증가를 고려해야 함)

#### 13. RemoteMessageHandlerManager — static 딕셔너리와 인스턴스 혼용
**파일**: `Library/MessageQueue/Attributes/Remote/RemoteMessageHandlerManager.cs:9-11`

```csharp
private static readonly Dictionary<...> _syncHandlers = new();
private static readonly Dictionary<...> _asyncHandlers = new();
```

static 필드를 인스턴스 메서드에서 조작한다. MessageQueueDispatcher가 싱글톤이어서 실질적 문제는 없지만, 인스턴스를 여러 개 만들 경우 state가 공유되는 의외의 동작이 생긴다. static 클래스나 명시적 싱글톤 패턴으로 통일하는 것이 의도를 명확히 한다.

## 잘된 점

- **Channel 기반 액터 모델**: `IMessageQueue` + `Channel<T>` 조합으로 락 없이 세션 격리. `SingleReader = true` 옵션으로 리더 경합도 제거.
- **SessionId % N 샤딩**: 동일 유저가 항상 동일 TickThreadWorker에서 실행되어 유저 내부 상태 잠금이 불필요.
- **SenderHandler 원자적 전송 제어**: `Interlocked.CompareExchange`로 `_isSending` 플래그 관리. Lost Wakeup 방어 코드(큐 재확인 후 재시도)가 명확히 구현됨.
- **stale 콜백 차단**: `OnSendCompleted`에서 `ReferenceEquals(sender, _socket)`으로 세션 교체 후 들어오는 오래된 완료 콜백을 차단.
- **ReceiveParser 상태 기계**: Header/Body 2단계 상태 기계로 TCP 분할 수신 처리. partial 데이터를 버퍼 앞으로 compaction하는 로직이 정확.
- **PasswordHashHelper**: 서버 저장 해시에 PBKDF2(100,000회) + random salt + `CryptographicOperations.FixedTimeEquals` 적용. 타이밍 공격 방어까지 갖춤.
- **IP 플러드 차단**: Queue<DateTime> + lock으로 슬라이딩 윈도우 구현. `SweepExpiredIfDue`에서 CAS로 단일 스레드만 정리 작업을 수행하는 구조.
- **RemoteReceiveMessage 오브젝트 풀**: `ConcurrentQueue` + Interlocked increment-first 패턴으로 pool 상한 보장.
- **KeepAlive 타임아웃**: `Stopwatch.GetTimestamp()` 기반으로 tick마다 인증 세션의 keepalive 만료 여부 확인. 정수 연산으로 부동소수점 오차 없음.

## 동시성 / 스레드 안전성

| 항목 | 상태 | 비고 |
|------|------|------|
| 세션 내 상태 접근 | ✅ | TickThreadWorker 단일 스레드에서만 처리 |
| 세션 채널 enqueue | ✅ | Channel<T>의 TryWrite는 thread-safe |
| SenderHandler 전송 플래그 | ✅ | Interlocked + Lost Wakeup 방어 구현됨 |
| RegisterAuthenticatedSession | ❌ | TryGetValue + [] 비원자 복합 연산 → 중복 로그인 가능 |
| ReceiveParser | ✅ | 단일 소켓 콜백에서만 호출 |
| ObjectPool.Return() | ⚠️ | ConcurrentQueue는 thread-safe하나 크기 한도 미확인 |
| TimerScheduleManager.Tick() | ⚠️ | lock을 짧게 잡고 timer 실행은 락 밖에서 — 정상. 비동기 타이머는 fire-and-forget으로 Tick 블로킹 없음 |
| SessionIdGenerator | ✅ | Interlocked.Increment 사용 |
